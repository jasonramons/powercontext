# 一页技术说明 · seekdb 迷你知识库

## 1. 架构与数据流

```
浏览器                                    本地 Node 服务
┌──────────────────────────┐            ┌───────────────────────────┐
│ 文本 → 切分 → Transformers│  向量+原文  │ Express API                │
│ .js 推理（WebGPU / WASM） │ ─────────► │   ↓                        │
│ 查询 → 同一模型向量化      │  查询向量   │ seekdb（嵌入式 server 进程）│
│ 渲染结果 + 引用            │ ◄───────── │  kb_chunks：向量 + 全文 + 元数据│
└──────────────────────────┘   命中结果   └───────────────────────────┘
```

关键约束：**embedding 只在浏览器发生**。服务端 `/api/ingest` 接收的是已经算好的 384 维向量，维度不符直接拒绝；`/api/search` 接收查询向量后调用 seekdb 的 `hybridSearch`，融合在数据库内部完成。

## 2. 模型与量化

| 项 | 取值 |
|---|---|
| 模型 | `Xenova/all-MiniLM-L6-v2`（ONNX 导出，Apache-2.0），输出 384 维 |
| 后端选择 | 探测到 WebGPU 用 `fp16`；否则退到 WASM 用 `q8`（INT8） |
| 权重体积 | FP32 86.2 MB → **FP16 43.2 MB**（50.1%）→ **INT8 21.9 MB**（25.4%） |

量化方案说明：FP16 只压权重精度，WebGPU 上通常有 1.5～2× 提速且质量损失可忽略；INT8 把权重压到四分之一，适合没有 GPU 的机器，代价是少量精度损失。

**量化质量对比未在本机完成**：本机没有可自动化的浏览器环境，无法测出 FP16 与 INT8 在同一批查询上的 Recall 差异。建议复测方法：固定 30 条查询 + 人工标注，分别用两种 dtype 跑 Recall@5 与 MRR，再决定默认档位。

## 3. 运行时与降级

- 启动时 `navigator.gpu.requestAdapter()` 探测；无 `navigator.gpu`、无适配器或探测抛错都走 WASM。
- 降级原因会直接显示在右上角徽标（例如「后端 WASM（未取到 GPU 适配器）」），不静默切换。
- ONNX Runtime 的 WASM 运行时随包构建（`ort-wasm-simd-threaded.jsep` 21.6 MB），不依赖 CDN；模型权重首次加载从 HF 下载并进浏览器缓存，可用 `VITE_HF_ENDPOINT` 指向镜像。

## 4. seekdb 的使用

| 项 | 做法 |
|---|---|
| 部署方式 | 嵌入式 server 模式：`@oceanbase/seekdb-node` 拉起本地进程，SDK 拿到随机 TCP 端口后连接 |
| 集合 | `kb_chunks`，384 维，距离度量 cosine，HNSW 索引 |
| 记录 | 向量 + 原文 + 元数据（`document_id` / `source` / `chunk_index` / `chars`） |
| 写入 | `upsert`，同一 `documentId` 重复导入幂等覆盖 |
| 混合检索 | `hybridSearch`：全文 `whereDocument.contains` + 向量 `knn`，`rank.rrf`（k=60）在库内融合 |
| 纯向量检索 | 同一路径去掉全文子句，只给 `knn`，排序完全由 seekdb 的向量距离给出 |
| 增量/删除 | 重新导入覆盖同 id 片段；按 `document_id` 过滤删除 |

全文子句取查询文本前 64 个字符作为 `contains` 关键词，避免整句当短语导致召回过窄；即使全文一路零命中，向量一路仍会返回结果。

## 5. 性能（本机实测，Node 22 / Windows 11 x64）

| 指标 | 数值 |
|---|---|
| seekdb 启动（冷） | 5.8 s |
| seekdb 启动（已有数据目录） | 1.9 s |
| 写入 9 个片段（upsert） | 28～46 ms |
| 纯向量检索（5 结果） | 4～9 ms |
| 混合检索（5 结果，冷） | 148 ms（首次建全文索引） |
| 混合检索（5 结果，热） | 6 ms |
| 前端 bundle | 877 KB（gzip 234 KB）+ ORT WASM 21.6 MB |

已做的优化：

1. **批量向量化**：每批 8 条送入模型，减少推理调用次数。
2. **切分策略**：段落优先、500 字目标、80 字重叠，减少跨块事实被切断。
3. **幂等写入**：`upsert` 避免重复导入产生重复片段。
4. **冷启动预热**：混合检索首次调用会建全文索引（148 ms），之后稳定在个位数毫秒。

浏览器侧（模型加载耗时、单条 embedding 延迟）需在真实浏览器中测量，页面底部指标栏会直接显示：模型加载秒数、检索端到端耗时（含查询向量化）。本次开发环境无可自动化浏览器，故未填入具体数字。

## 6. 状态一致性

- 每次导入以 `documentId` 为单位，先算完全部向量再一次提交，避免半写入。
- 检索无状态：查询向量每次现算，不缓存，避免"索引更新后仍用旧向量"。
- 服务端指标（`/api/health`）返回片段总数与调用计数，可用于核对"导入后条数是否一致"。

## 7. 已知限制

- 混合检索的全文一路用 `contains` 关键词，不是分词相关性排序；中文长句靠向量一路兜底。
- 单集合单维度：换模型（不同维度）需重建集合。
- 无鉴权：服务默认只监听本地回环，不要直接暴露到公网。
